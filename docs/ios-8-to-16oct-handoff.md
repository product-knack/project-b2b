## A1. Client health summary card, the listen gate and the summaries strip (9 Oct 2026; read repaired 15 Oct; roster strip 16 Oct)

**Why.** Trainers, doctors, therapists and CRM hear a client's two short spoken overviews before a session ("Listen before the session"), and every play is recorded with who and when. A session logged from Today's Roster is gated behind it: this week's training heard every day, the health context heard whenever a new report rebuilt it (owner, 9 Oct 2026: "make it mandatory ... daily wala daily, weekly wala jab bhi new report se update ho").

**Backend (live, since 9 Oct 2026; one row per training day since 10 Oct; Essentials listeners since 15 Oct).** Nothing to run on the server. Migrations in hub-track: `20261009100000` (table, RLS, RPC, triggers, crons), `20261009110000`, `20261009120000`, `20261010160000_client_health_summary_daily_rows.sql` (primary key `(client_id, briefing_date)`, the read RPC), `20261015160000_listen_summary_essentials_bidders.sql`.
- Table `client_health_summary`: **never select it directly** (the 9 Oct direct read broke on 10 Oct with `42703` and hid the card for five days). Read through the RPC below. The app never inserts, updates or deletes.
- `get_client_health_summary(p_client_id uuid, p_date date DEFAULT NULL) RETURNS TABLE (client_id uuid, briefing_date date, status text, built_at timestamptz, weekly_summary jsonb, context_summary jsonb, listen_history jsonb, has_quiz boolean, auction_result text, context_dirty boolean)`, SQL STABLE SECURITY DEFINER, `authenticated` only (anon revoked). Returns 0 or 1 row: the latest row with `briefing_date <= COALESCE(p_date, today IST)` for which `can_listen_client_summary(p_client_id)` is true. `status` is `'building'` or `'ready'`. The app ignores `has_quiz` and `auction_result`.
- `weekly_summary` jsonb: `{generated_at, window_from, window_to, script, highlights[] (up to 3 strings), version, fallback, fallback_reason, facts{...}}`. `context_summary` jsonb: `{generated_at, script, sources[{type blood|qhp|medical|report, id, date, label}], improved[], worsened[], watch[] (each {key, label, text, value, previous, unit, date}), medical_events[], exclusions_confirmed, version, fallback, fallback_reason, ...}`. `listen_history` jsonb array, oldest first: `[{at, by (profile id), by_name, role, which 'weekly'|'context', version, briefing_date}]`.
- `log_summary_listen(p_client_id uuid, p_which text) RETURNS jsonb`, plpgsql SECURITY DEFINER, `authenticated` only. Appends `{at, by, by_name, role, which, version, briefing_date}` to the row in effect **today** (latest `briefing_date <= today IST`, never the dated row the strip shows) and returns that entry; the trail is capped at 500 entries. Raises plain sentences: `which must be weekly or context`, `Not allowed to listen to this client's summary`, `No summary on file for this client yet`. `PGRST202` (function missing) is shown as "The listen trail is not set up on the server yet.".
- `can_listen_client_summary(p_client_id uuid) RETURNS boolean` (the single gate for the table policy, both RPCs and the voice function): admin, a trainer of the client (`is_trainer_for_client` or `trainer_has_client_access`), any doctor or therapist, CRM and managers, and since 15 Oct 2026 **any `trainer` or `coach` when the client is on the Essentials plan** (`essentials_is_plan(clients.subscription_type)`), because the auction offers those clients to everyone. An unauthorised caller gets no row, not an error; the app cannot tell "no row" from "not allowed".
- `get_client_health_summary_history(p_client_id uuid, p_limit int DEFAULT 14)` exists (older days, light fields) but Android does not call it; the "Previous days" list of the 10 Oct web handoff was not built on Android and is not required here.
- Builds (server side, nothing for the app): tomorrow's row at 1:00 AM IST for every active client; the context rebuilt within a minute of a new blood report, QHP, medical record or analysed health report. The card copy still says "Built nightly at 11:59 PM"; keep the copy as written.

## A2. Sarvam voice for the summaries and one sound at a time (15 and 16 Oct 2026)

**Why.** The owner wants the summaries in Sarvam's Indian English voice "as in my web b2b app", with the device voice only as the fallback so the gate can always be cleared. And a second Play anywhere must silence the first ("if play one and we click another play the previous automatically stops"), across summary cards, strips, the gate, voice notes, voice memos, messenger voice messages and the Nucleus article audio.

**Backend (live, since 9 Oct 2026 on the web, used by Android since 15 Oct).** Nothing to run on the server; the function, the bucket and the secret are the web session's. Edge function `speak-client-summary` (hub-track `supabase/functions/speak-client-summary/index.ts`, deployed):
- Request: `POST /functions/v1/speak-client-summary`, header `Authorization: Bearer <the signed-in user's access token>` (the Sarvam key is a server secret `sarvam_key`; nothing for the app), JSON body `{ client_id: uuid, which: 'weekly' | 'context', briefing_date?: 'YYYY-MM-DD' }`. Without `briefing_date` the row in effect today (latest `briefing_date <= today IST`); with it, exactly that day's row. The function reads `client_health_summary` with the caller's token, so `can_listen_client_summary` decides.
- Response 200: `{ urls: string[], parts: number, version: number, briefing_date: 'YYYY-MM-DD', cached: boolean, speaker: 'priya', model: 'bulbul:v3' }`. `urls` are one-hour signed MP3 links (`audio/mpeg`), the parts of one recording in order; play them back to back. **Rules.**
- The trail (`log_summary_listen`) is written by the caller before `play`, never by the voice.
- Order of attempts on Play: the recording (function → signed parts); on ANY failure (function error, timeout, offline, empty `urls`, player `error`, a part that never starts within 15 s, `makePlayer` throwing) the device voice reads the same script with the notice; only when the device voice fails too does `onError` fire (the transcript opens; in the gate the item counts as heard). Offline the function call fails fast and the device voice reads at once, so the gate can be cleared offline too.
- One sound at a time across the whole app; navigation turn cues are exempt (short, must never cut a summary off).
- `onDone` fires once per run: after the last part's `didJustFinish` (recording) or the last sentence (device voice). An outside stop, a user stop, pause or a second Play never fires it.
- The gate's "heard" uses `onDone`; the card and the strip ignore it.
- The strip asks for its card's training day (`briefing_date`); the card and the gate ask for today's row (no date).
- iOS physical devices with the silent switch on produce no `expo-speech` sound; the recording plays because `playsInSilentMode` is set; the transcript toggle is the last resort.
- The first play of a new summary version takes a few seconds (Sarvam renders); a later play of the same version only signs.

## C3. Essentials plan alert and the Odds AI plan assistant with NOT IN DB exercises (16 Oct 2026)

**Why.** An Essentials client whose session a trainer wins in the auction often has no valid plan, and the winner is often not the client's assigned trainer; the home alert says "Make {client}'s workout plan" and Create Plan drafts it with Odds AI from the client's QHP, medical and blood data, into the normal form the trainer edits.
